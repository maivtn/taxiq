# Design: Merchant Sub Accounts, Roles, and Activity Logs

- **Date:** 2026-08-07
- **Status:** Draft - ready for product/API review
- **Scope:** Settings module for merchant owner accounts

## 1. Goal

Allow a merchant owner to create staff sub accounts, assign each sub account to a configurable role, control which merchant dashboard modules each role can access, and review activity logs generated by sub accounts.

The feature lives under merchant **Settings** and has three tabs:

- **Sub Accounts**
- **Roles**
- **Activity Logs**

## 2. User Roles

### Owner

The owner is the main merchant account. The owner always has full access to all modules and can manage sub accounts, roles, and logs.

### Sub Account

A sub account is a login account created by the owner for a staff member. A sub account can sign in with email and password and access only the merchant modules enabled by its assigned role.

## 3. Settings Structure

Add a new Settings section named **Sub Accounts** or **Team Access**.

Inside this section, show three tabs:

1. **Sub Accounts** - manage staff login accounts.
2. **Roles** - manage role names and module permissions.
3. **Activity Logs** - review sub account activity.

## 4. Tab: Sub Accounts

### 4.1. Sub Accounts List

The list screen shows all sub accounts created under the merchant.

#### Filters

- Search by display name, email, or phone
- Status filter
- Role filter
- Rows per page
- Go to page

#### Table fields

- **Display Name**
  - Avatar initials
  - Display name
  - Sub account ID below the name
- **Email**
  - Email address
  - Phone number below the email when available
- **Role**
  - Role badge
- **Status**
  - Status badge
- **Last Login**
  - Last successful login datetime
- **Actions**
  - View
  - Edit
  - Activate or Deactivate
  - Reset password
  - Resend login email

#### Status values

- **Active** - can sign in and use enabled modules.
- **Disabled** - cannot sign in.
- **Pending** - account was created but first login has not happened yet.

### 4.2. Add New Staff Modal

The owner creates a sub account from a modal named **Add New Staff**.

#### Fields

- **Email** - required
- **Password** - required, minimum 6 characters
- **Role** - required, selected from existing roles
- **Display name** - optional
- **Phone** - optional, with country code

#### Validation

- Email must be present and valid.
- Password must be at least 6 characters.
- Role must be selected.
- Phone is optional, but if entered it must use a valid phone format.

#### Info box

The modal shows a preview explaining that the system will email login details to the staff account.

Example:

```text
After the staff is created, the system will email the login details to this account:

Email: mary.smith@mailinator.com
Password: ***
Login link: https://staging-merchant.vlinkpay.com/staff/login?merchant=...
```

If email is empty, show:

```text
Email: -
Password: ***
Login link: https://staging-merchant.vlinkpay.com/staff/login?merchant=...
```

#### Submit behavior

When the owner clicks **Create Staff**:

1. Frontend sends email, password, role ID, optional display name, and optional phone to the backend.
2. Backend creates the sub account.
3. Backend assigns the selected role.
4. Backend sends a login email to the sub account.
5. Frontend refreshes the sub account list.

#### Success and error messages

- Success: `Staff account created and login email sent.`
- Partial success: `Staff account created, but login email could not be sent.`
- Failure: show the backend validation or error message.

### 4.3. Sub Account Detail

Clicking **View** opens the sub account detail screen or drawer.

#### Fields

- Display name
- Email
- Phone
- Role
- Status
- Created at
- Last login
- Login URL
- Effective module permissions inherited from role

#### Actions

- Edit account info
- Change role
- Reset password and send new login email
- Resend login email
- Activate or Deactivate

## 5. Tab: Roles

### 5.1. Roles List

The Roles tab shows the list of roles the owner has configured.

#### Table fields

- **Role**
  - Shield icon
  - Role name
- **Permissions**
  - Count of enabled modules, for example `8 modules enabled`
- **Staff**
  - Number of sub accounts assigned to this role
- **Daily Limit**
  - Show `-` in V1
- **Actions**
  - View or Edit
  - Delete

#### Actions

- Add Role
- View/Edit role
- Delete role

#### Delete rule

A role cannot be deleted when one or more sub accounts are assigned to it. The owner must move those sub accounts to another role before deleting the role.

### 5.2. Add/Edit Role

The owner creates or updates a role from the role detail screen.

#### Fields

- **Role Name** - required, max 100 characters
- **Module switches**
  - Dashboard
  - Staff
  - Payments & Payouts
  - Transactions
  - Reviews
  - Touchpoints
  - AI Hub / Booking
  - Gift Card Center
  - Analytics
  - Settings
  - Support

#### Behavior

- Each module is controlled by an on/off switch.
- The owner can enable or disable all modules in a group when group switches are supported.
- Saving a role updates effective permissions for all sub accounts assigned to that role.

### 5.3. Role Detail

The role detail screen follows this structure:

- Back button
- Title: `Role Detail`
- Subtitle: `Configure permissions for this role`
- Role card
  - Shield icon
  - Role name
  - Role ID
- Role Name input
- Permission groups and module switches
- Save changes button
- Delete role button when allowed

### 5.4. Permission Model

V1 permission is module-level only. There is no separate view/manage permission in V1.

```ts
type RoleModules = {
  dashboard: boolean
  staff: boolean
  payments: boolean
  transactions: boolean
  reviews: boolean
  touchpoints: boolean
  aiHub: boolean
  giftCard: boolean
  analytics: boolean
  settings: boolean
  support: boolean
}
```

### 5.5. Permission Groups

Use these groups for the role detail UI:

#### Business

- Dashboard
- Staff
- Settings
- Support

#### Payments & Reports

- Payments & Payouts
- Transactions
- Analytics

#### Customer Experience

- Reviews
- Touchpoints
- AI Hub / Booking

#### Commerce

- Gift Card Center

## 6. Tab: Activity Logs

### 6.1. Activity Logs List

Activity Logs show the actions performed by sub accounts.

#### Filters

- Search by name, email, or action
- Sub Account
- Role
- Module
- Status
- Date range

#### Table fields

- Time
- Sub Account
- Email
- Role
- Action
- Module
- IP Address
- Device / Browser
- Status

#### Status values

- Success
- Failed

### 6.2. Log Examples

- Login success
- Login failed
- Created appointment
- Updated staff
- Viewed transactions
- Changed settings
- Deactivated staff
- Exported report
- Reset password
- Role changed

### 6.3. Log Creation Rules

The backend should create activity logs for security-sensitive and business-sensitive actions.

Minimum logged events:

- Sub account login success
- Sub account login failure
- Sub account logout
- Create, update, or delete staff data
- Create, update, or delete touchpoint data
- View or export transaction/report data
- Update settings
- Reset password
- Role assignment changed
- Sub account activated or deactivated

## 7. Login Email Flow

After the owner creates a sub account, the backend sends a login email to that sub account.

### Email content

- Merchant or store name
- Login URL
- Email
- Password or temporary password
- Assigned role
- Message telling the staff member to sign in

### Recommended security behavior

The preferred flow is a setup-password link or temporary password that expires.

If V1 uses the password entered by the owner, the backend should require the sub account to change password after first login.

### Resend login email

The owner can resend the login email from the sub account list or detail screen.

### Reset password

The owner can reset a sub account password. After reset, the backend sends a new login email.

## 8. Routing and Permission Enforcement

### Owner access

Owner accounts always have access to all merchant dashboard routes and all Settings tabs.

### Sub account access

Sub accounts can access `/dashboard` only when authenticated and attached to a merchant account.

Frontend must:

- Hide menu items for modules that are off.
- Hide mobile bottom-nav items for modules that are off.
- Block direct URL access to disabled modules.
- Show a permission denied screen when a sub account opens a disabled module route directly.

Backend must:

- Enforce the same permissions on protected APIs.
- Reject disabled module actions even if the frontend is bypassed.

## 9. Session Shape

After login, the session should include enough data for frontend route/menu enforcement.

```ts
type SubAccountSession = {
  role: 'sub_account'
  merchantId: string
  subAccountId: string
  roleId: string
  modules: {
    dashboard: boolean
    staff: boolean
    payments: boolean
    transactions: boolean
    reviews: boolean
    touchpoints: boolean
    aiHub: boolean
    giftCard: boolean
    analytics: boolean
    settings: boolean
    support: boolean
  }
}
```

## 10. API Contract Needed

### Roles

```http
GET /api/v1/merchant/roles
POST /api/v1/merchant/roles
PUT /api/v1/merchant/roles/{roleId}
DELETE /api/v1/merchant/roles/{roleId}
```

### Sub Accounts

```http
GET /api/v1/merchant/sub-accounts
POST /api/v1/merchant/sub-accounts
GET /api/v1/merchant/sub-accounts/{accountId}
PUT /api/v1/merchant/sub-accounts/{accountId}
POST /api/v1/merchant/sub-accounts/{accountId}/enable
POST /api/v1/merchant/sub-accounts/{accountId}/disable
POST /api/v1/merchant/sub-accounts/{accountId}/resend-login-email
POST /api/v1/merchant/sub-accounts/{accountId}/reset-password
```

### Activity Logs

```http
GET /api/v1/merchant/sub-account-activity-logs
```

The logs endpoint should support pagination and filters for search, sub account, role, module, status, and date range.

## 11. Out of Scope for V1

- Per-action view/manage permissions
- Daily limits
- Approval workflow for role changes
- Multi-merchant role templates
- Staff self-service role requests

## 12. Acceptance Criteria

- Owner can create a role with a name and module switches.
- Owner can edit a role and the change applies to assigned sub accounts.
- Owner cannot delete a role that has assigned sub accounts.
- Owner can create a sub account with email, password, role, optional display name, and optional phone.
- Backend sends the login email after sub account creation.
- Owner can resend login email.
- Owner can reset password and send a new login email.
- Owner can activate or deactivate a sub account.
- Disabled sub accounts cannot sign in.
- Sub accounts only see modules enabled by their role.
- Sub accounts cannot access disabled modules by typing a URL directly.
- Activity Logs tab shows sub account actions with filters and pagination.
- Owner always has full access regardless of role records.
